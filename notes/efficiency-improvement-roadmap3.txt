Efficiency Improvement Roadmap 3

Date: 2026-05-29
Project: Hephaestus
Document: notes/efficiency-improvement-roadmap3.txt

Abstract
Hephaestus can recover from efficiency regression when queue governance, ticket quality, and policy-runtime compatibility are tuned as a single control loop. Prior high-volume experiments (60 and 120 tickets) exposed a core failure mode: orchestration throughput increased while code-delivery throughput plateaued or regressed due to broad envelopes, denial friction, and supersede churn. This roadmap defines a practical recovery strategy focused on constrained admission, wave-gated execution, friction burn-down, and measurable output quality.

Current Failure Pattern
The regression pattern is now clear:
- queue volume outran deterministic execution capacity
- non-bounded tickets triggered unsupported envelope paths
- verification command mismatch triggered allowlist denials
- high supersede/blocked ratios diluted meaningful completion

Hephaestus therefore shifted from accelerator to amplifier of queue noise.

Roadmap Goals
1. Restore net-positive efficiency trend over rolling windows.
2. Increase completed-code output per wave while reducing churn.
3. Make denial/supersede root causes actionable within one iteration cycle.
4. Right-size queue depth to match present policy/runtime capability.

Phase A: Admission Hardening And Scope Normalization (Days 1-3)
Goal: eliminate low-probability tickets before they consume execution budget.
- Enforce bounded ticket contract:
  - single local subsystem focus
  - deterministic verification command from approved set
  - explicit expected signal clause
  - low blast radius file scope
- Reject broad multi-surface tickets at intake.
- Auto-split broad intents into bounded child tickets before queue admission.
Deliverables:
- stricter template validation
- explicit intake rejection reasons
- ticket quality score distribution in telemetry

Phase B: Policy Friction Reduction (Days 2-5)
Goal: reduce avoidable blocked states from command mismatch.
- Normalize accepted verification command variants.
- Add bounded targeted test patterns to runtime allowlist.
- Convert denial messages into stable reason-code buckets for trend tracking.
Deliverables:
- reduced allowlist denial rate
- reason-code top-3 dashboard integrity
- lower blocked growth per execution wave

Phase C: Wave-Gated Queue Control (Days 4-7)
Goal: control queue pressure and prevent churn cascades.
- Execute in waves of 5-10 tickets only.
- Cap active queue at 20-40 tickets.
- Gate new wave admission on hard thresholds:
  - completion rate >= 0.70
  - superseded rate <= 0.20
  - blocked growth <= +5
  - allowlist denial rate <= 0.08
- When any gate fails: pause new waves and run remediation-only wave.
Deliverables:
- enforced wave slot accounting
- gate failure reporting in operator output
- stable queue pressure index movement

Phase D: Root-Cause Observability And Weekly Burn-Down (Week 2 onward)
Goal: convert telemetry into direct operational leverage.
- Maintain two scorecards:
  - delivery score: completions/day, latency, completion ratio
  - governance friction score: denial rate, envelope rejects, supersede causes
- Publish top-3 root causes each cycle:
  - top deny reason
  - top supersede reason
  - top retry reason
- Require each remediation wave to target at least one top-3 cause.
Deliverables:
- actionable root-cause telemetry fields
- trendable failure taxonomy quality
- weekly remediation closure loop

Phase E: Volume Strategy Recalibration
Question: should overall ticket count be lower?
Answer: yes, until friction metrics stabilize.
- 120-ticket batches: currently too coarse and churn-heavy.
- 60-ticket batches: better but still over-capacity under denial-heavy policy behavior.
- Recommended operating mode now:
  - 20-40 active tickets max
  - 5-10 ticket execution waves
  - backlog promotion only when gates pass

Why this works:
- lower active depth increases signal fidelity
- faster adaptation on top failure buckets
- less supersede debt from stale broad tasks
- clearer causality between interventions and metric deltas

Execution Protocol
1. Capture pre-wave snapshot.
2. Run one bounded wave.
3. Evaluate hard gates.
4. If pass, admit next wave.
5. If fail, run remediation-only wave.
6. Re-snapshot and compare.
7. Continue until 3 consecutive positive waves.

Success Metrics (Rolling 7-day)
- completion rate >= 0.70
- superseded rate <= 0.20
- allowlist denial rate <= 0.08
- blocked-retry success ratio improving week-over-week
- efficiency index trend positive across 3 consecutive snapshots

Risk Controls
- prevent unlimited retry loops on low-quality tickets
- freeze bulk seeding during friction spikes
- cap active queue growth and enforce wave slots
- prioritize remediation over new feature intake when gates fail

Conclusion
Hephaestus regains efficiency by acting as a constrained execution controller, not a volume-first queue sink. The combination of strict admission, low-friction verification policy, wave-gated queueing, and root-cause remediation can convert the system back into a compounding engineering accelerator.
